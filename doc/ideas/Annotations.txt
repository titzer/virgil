Annotations on various constructs are useful in a variety of other programming
languages.  This note explores ideas some ideas for annotations in Virgil.

We start from the annotations design for Java.  They use @interface to define
an annotation.  The sensible correlate for Vigil is @type.  We will use Java's
@deprecated as a running example.  The simplest form of an annotation is one
with no additional information attached:

@type deprecated;

This declares an annotation that is used by writing:

@deprecated

We did not specify what kind of thing can be annotated with this annotation,
so it can be used any place where we allow an annotation.  To indicate the
desired kind of target, use the meta-annotation Target:

@target(TargetKind.Class)
@type deprecated_class;

Here are possible annotation targets, which are members of the built-in enum
TargetKind; we may not include / support all of these:

- Program: can be applied to a program, which must be done on the command
  line; possible syntax: -@program=<annotation>
- File: can be applied to a file on the command line, or in the file; possible
  syntax (command line) -@file=<filename>=<annotation> or (in file)
  @file(<annotation>).
- AnnotationType, i.e., this is a meta-annotation; possible syntax: prefixed
  to @type
- Field: of a class, component, variant, or enum; possible syntax: prefixed to
  def/var/def var; alternate syntax: just after def/var/def var
- Formal: argument declaration of a method; to annotate the receiver of a
  method, include "this" explicitly, e.g., def m(@readonly this, int i) { ... };
  possible syntax: immediately before the parameter name
- Actual: argument expression in a call; possible syntax: immediately before
  the expression
- Local (variable) in a method; possible syntax: as for a field
- Parameter: formal type parameter of a class, etc.; possible syntax:
  immediately before the identifier
- TypeUse: in a declaration, constructor, etc.; possible syntax: immediately
  before the type use
- Method: possible syntax: as for a field
- Class, Variant, Component, Enum: possible syntax: immediate before keyword
  ('class', etc.); alternate: immediately after
- Block; possible syntax: immediately before opening {
- Statement; possible syntax: immediately before statement (note: by putting
  extra { } around a statement, we can use block annotations instead)
- Expression; possible syntax <annotation> (<expr>) (note: there is a space
  between <annotation> and (<expr>); the required parentheses will reduce
  ambiguity)

Of these, the ones for statements and expressions could potentially lead to
the greatest internal burden in the compiler, and some degree of "friction"
between the user's view (which follows the AST) and internals (SSA).  I think
we need more compelling use cases before adding those.  Annotations on
declarations and structural forms have more obvious uses.  For the approach to
using annotations for atomic actions that is outlined below, we would use
these targets: Program, File, AnnotationType, Field, Parameter, TypeUse,
Method, Class/Variant/Component/Enum, and Block.  That is, Formal, Actual,
Local, Statement, and Expression are not needed.

@target may be repeated to allow annotations of a given type to be attached to
more than one kind of thing.  This can be done via:

@target(TargetKind.Class)
@target(TargetKind.Variant)
@target(TargetKind.Enum)
@type deprecated;

Use of repeating annotations can also be written this way:

@target([TargetKind.Class, TargetKind.Variant, TargetKind.Enum])
@type deprecated;

To make your own annotation repeatable, use the meta-annotation @repeatable.

We may organize targets into groups (enum sets) to make it easier to specify
logically related kinds of targets.  Here are some ideas:

- Declaration: Field, Formal, Local, Parameter, Method, Class, Variant, Component, Enum
- Container: Class, Variant, Component, Enum, File, Program
- Code: Method, Block, Statement, Expression, Constructor

Note that since the targets are drawn from an enum, these are just some
predefined enum sets.

Java has an @Retention meta-annotation that indicates how far through the
compilation process the annotation is kept.  It allows retentions of source,
class (compiler), and run-time.  Allowing run-time retention may have
undesirable cost, and Virgil does not have much in the way of run-time
reflection.  Still, some run-time annotations might be useful, such as to
indicate object allocations that should go to particular allocation areas, and
so forth.  For our current use cases, Source and Compiler retentions make the
most sense.  Source ones would be parsed and checked, but probably dropped at
some point in the compilation process.  Compiler ones would be kept throughout
SSA.


More complex annotations

Annotations may have fields, which must be immutable values.  This includes
integer and floating point types, enums, enum sets, strings, and ADTs and
read-only arrays whose elements are immutable, as well as other annotations.
For example:

@target(TargetKind.Declaration)
@type deprecated(why: string = "");

This indicates that @deprecated can come with a reason why the construct is
deprecated, and that the default value for the "why" field is the empty string.
If the initializer is omitted, the default value will be the default value of
the type (which would be null for string).  The default value is supplied if
the user writes

@deprecated

or

@deprecated()

To require that the user supply a value, use the meta-annotation @required:

@target(TargetKind.Declaration)
@deprecated(@required why: string)

The fields of an annotation can be provided positionally or by keyword, or
both, and defaults may be supplied.  The procedure is:

1.  Associate any values supplied by keyword.  A given keyword may appear only
    once, unless it is marked @repeatable.

2.  Associate positional values to the field not yet assigned, left to right.

3.  Default any remaining fields, but give an error if any are @required.

Assuming we have a value type Date, we could this define:

@target(TargetKind.Declaration)
@type deprecated(@required since: Date, why: string = "");

Some possible uses of this include:

@deprecated(why="use foo instead", Date(2026, 8, 1))
@deprecated(Date(2026, 8, 1), "use foo instead")
@deprecated(Date(2026, 8, 1))


Implicit annotations

To help relieve annotation burden, we support *implicit* annotations,
typically derived from related annotations on containing structures.  Let's
consider how we would set up a highly implicit system of @atomic, etc.,
annotations for the transactional memory extension to Virgil.

// The allowed "kinds" of atomicity
enum Atomicity { Nonatomic, Atomic, Relaxed }

// Enum set computation here (TODO: check for Virgil syntax)
def AtomicTargets = [TargetKind.Container, TargetKind.Code, TargetKind.Field];

// This calculates implied Atomicity using @or (first available argument)
@target(AtomicTargets)
@implicit(@or(@outer.atomicity, Atomicity.Nonatomic)
        // Note: @outer is never defined for the overall program, so the @or
        // means that the default atomicity is Nonatomic, and the use of
        // @outer means it will propagate inward until an explicit annotation
        // overrides it.
@type atomicity(value: Atomicity) {
    def atomic_ok() => value != Atomicity.Nonatomic;
    def nonatomic_ok() => value != Atomicity.Atomic;
}

// shorthands to obtain desired conciseness
@define @atomic    = @atomicity(Atomicity.Atomic);
@define @nonatomic = @atomicity(Atomicity.Nonatomic);
@define @relaxed   = @atomicity(Atomicity.Relaxed);

None of the above does anything to a type *use* automatically.  We add this to
allow the possibility, but to make it manually controlled:

@target(TargetKind.TypeUse)
@clones_type(@atomic) // means that:
	// a) The annotation version of the type is distinct from the
        //    unannotated version.
        // b) Each different annotation version leads to a distinct type.
        //    (Here we have only @atomic and unannotated.)
        // c) The @atomic annotation (what's in the @clones_type) is what will
        //    be put on the type and is what distinguishes clones of the type.
	// @clones_type takes a list of annotation to place on the cloned type.
@type atomic;
        // Note: This is distinct from the @atomic above, because the targets
        // are different.

Summary of additional machinery:

- @implicit: means that annotation is implicitly supplied on any included
  targets where an explicit annotation does not appear
- @or
- @this: means the current target; can be used to fetch annotation values
- @outer.Ann: means the immediately containing target of a kind that supports
  Ann, and to get the value of Ann for that target

Examples:

class Vector<T> {
  var size: int;
  var elements: Vector<T>.@atomic Array<T>;
	// If Vector<T> has @atomic, then the Array<T> does
  ...
}

This adds the notation <type>.@<annotation-name>, for fetching the annotation
of that name, associated with the type in this context.

With the above, at outermost level and without any command line override, etc.,

def v1 = Vector<int>.new();
	// nonatomic all the way down

def v2 = @atomic Vector<int>.new();
	// atomic, both for Vector and its contained Array.
	// We think of this as "cloning" the Vector class, giving a new
        // version with the @atomic on the class.

def v3 = @atomic Vector<Array<int>>.new();
	// The Vector and its contained Array are @atomic, but the arrays *in* that
	// array are not.

def v4 = @atomic Vector<@atomic Array<int>>.new();
	// This makes the inner arrays atomic.

@atomic var v5 = Vector<int>.new();
	// The *variable* is atomic, but the objects it refers to are not.


Implementation

Given that parameterized types may need to be instantiated, and annotated type
uses may cause further type cloning, it would seem that full expansion and
determination of annotation values will not be complete until reachability
analysis and normalization finish.

An annotation on a @clones_type type use is a demand for an annotated
version of the type being used, as described by the @clones_type annotations to
add.  The clones are indexed by the annotation with the @clones_type in it, as
opposed to the annotations *in* the @clones_type annotation itself.  Those
annotations give guidance as to how to set implicit annotations, and any
specific explicit ones the @clones_type wishes to.

For example, the @clones_type(@atomicity(Atomicity.Atomic)) on the TypeUse
target for @atomic means that a type use of @atomic, such as
@atomic Vector<int> implies an @atomic clone of Vector<int> *and* that the
clone will have the annotation @atomicity(Atomicity.Atomic).  Other
implied/derived annotations will flow from that.

There is nothing to prevent cloning types such as 'int', but it is not
instantly obvious how to deal with getting values into and out of such types.
Generally, casting between clones of the same type may not be meaningful.
However, we could define it as the obvious projection between value types that
have different (or no) annotations.


Representation

Here is a sketch of representing annotations using compiler-generated ADTs.
Note: this is for individual annotations, not descriptions of annotation
*types*, which would be compiler data structures.

For brevity, I will start their names with A@ for regular annotation and AM@
for meta-annotations.  They can be arranged in a hierarchy along these lines:

enum TargetKind { Program, File, AnnotationType, Field, Formal, Actual, Local,
    Parameter, TypeUse, Method, Class, Variant, Component, Enum, Block, Statement,
    Expression, Constructor }

enum Retention { Source, Compiler }

type A@ { }  // root of the annotation hierarchy

type AM@ extends A@ { } // root of the meta-annotation hierarchy

type AM@target(value: TargetKind.set) extends AM@ { }
type AM@implicit extends AM@ { }
type AM@clones_type(value: A@) extends AM@ { }  // value may actually be an expr tree
type @AMrepeatable extends AM@ { }
type AM@retention(value: Retention) extends AM@ { }

type AMF@ extends AM@ { } // meta-annotation on an annotation field

type AD@(metas: List<AM@>) extends A@ { } // describes an annotation type

As a more extended example, here is the sketch A@ types for @deprecated,
@atomic, etc.:

type A@deprecated(why: string, date: Date) { }

type A@atomicity(value: Atomicity) { }

Instances of these could be attached to various compiler data structures,
initially AST nodes but then propagated to certain SSA structures.

It might be possible to avoid storing implicit derived annotations by
computing their value on demand - a lookup for a particular annotation could
trigger checking whether it is implicitly derived, and if so, then computing
it.  The value could be cached at the original place of demand (but not
necessarily at intermediate nodes).

The sue of hierarchy in these compiler-generated ADTs is intended to help the
compiler with checking what kind of annotation it is dealing with, but the
hierarchy is not deep - users cannot add levels to it because user annotation
declarations have no notion of subclassing or "extends".


Representing Annotation Types

An annotation *type* would include its list of meta-annotations and a list of
field declarations.  Each field declaration would need the name, type, and
default value expression (if any), as well as any meta-annotations on the
field.
