Annotations on various constructs are useful in a variety of other programming
languages.  This note explores ideas some ideas for annotations in Virgil.

We start from the annotations design for Java.  They use @interface to define
an annotation.  The sensible correlate for Vigil is @type.  The simplest form
is an annotation with no additional information attached:

@type Deprecated;

This declares an annotation that is used by writing:

@Deprecated

We did not specify what kind of thing can be annotated with this annotation,
so it can be used any place where we allow an annotation.  To indicate the
desired kind of target, use the meta-annotation Target:

@Target(TargetKind.Class)
@type DeprecatedClass;

Here are possible annotation targets, which are members of the built-in enum
TargetKind; we may not include / support all of these:

- Program: can be applied to a program, which must be done on the command line
- File: can be applied to a file on the command, or in the file by doing
  @myannotation @ThisFile
- AnnotationType, i.e., this is a meta-annotation
- Field: of a class, component, variant, or enum
- Formal: argument declaration of a method; to annotate the receiver of a
  method, include "this" explicitly, e.g., def m(@ReadOnly this, int i) { ... }
- Actual: argument expression in a call
- Local (variable) in a method
- Parameter: formal type parameter of a class, etc.
- TypeUse: in a declaration, constructor, etc.
- Method
- Class
- Variant (i.e., Virgil ADT)
- Component
- Enum
- Block
- Statement
- Expression

@Target may be repeated to allow annotations of a given type to be attached to
more than one kind of thing.  This can be done via:

@Target(TargetKind.Class)
@Target(TargetKind.Variant)
@Target(TargetKind.Enum)
@type Decprecated;

Use of repeating annotations can also be written this way:

@Target([TargetKind.Class, TargetKind.Variant, TargetKind.Enum])
@type Deprecated;

To make your own annotation repeatable, use the meta-annotation @Repeatable.

We may organize targets into groups (enum sets) to make it easier to specify
logically related kinds of targets.  Here are some ideas:

- Declaration: Field, Formal, Local, Parameter, Method, Class, Variant, Component, Enum
- Container: Class, Variant, Component, Enum, File, Program
- Code: Method, Block, Statement, Expression, Constructor

Java has a Retention meta-annotation that indicates how far through the
compilation process the annotation is kept.  It allows retentions of source,
class (compiler), and run-time.  Allowing run-time retention may have
undesirable cost, and Virgil does not have much in the way of run-time
reflection.  Still, some run-time annotations might be useful, such as to
indicate object allocations that should go to particular allocation areas, and
so forth.

More complex annotations

Annotations may have fields, which must be immutable values.  This includes
integer and floating point types, enums, strings, and ADTs and readonly arrays
whose elements are immutable, as well as other annotations.  For example:

@Target(TargetKind.Declaration)
@type Deprecated(why: string = "");

This indicates that Deprecated can come with a reason why the construct is
deprecated, and the the default value for the "why" fieldis the empty string.
If the initializaer is omitted, the default value will be the default value of
the type (which would be null for string).  The default value is supplied if
the user writes

@Deprecated

or

@Deprecated()

To require that the use supply a value, use the meta-annotation @Required:

@Target(TargetKind.Declaration)
@Deprecated(@Required why: string)

The fields of an annotation can be provided positionally or by keyword, or
both, and defaults may be supplied.  The procedure is:

1.  Associate any values supplied by keyword.  A given keyword may appear only
    once, unless it is marked @Repeatable.

2.  Associate positional values to the field not yet assigned, left to right.

3.  Default any remaining fields, but give an error if any are @Required.

Assuming we have a value type Date, we could this define:

@Target(TargetKind.Declaration)
@type Deprecated(@Required since: Date, why: string = "");

Some possible uses of this include:

@Deprecated(why="use foo instead", Date(2026, 8, 1))
@Deprecated(Date(2026, 8, 1), "use foo instead")
@Deprecated(Date(2026, 8, 1))


Implicit annotations

To help relieve annotation burden, we support *implicit* annotations,
typically derived from related annotations on containing structures.  Let's
consider how we would set up a highly implicit system of @Atomic, @Nonatomic,
and @Relaxed annotations for the transactional memory extension to Virgil.

// The allowed "kinds" of atomicity
enum Atomicity { Atomic, Nonatomic, Relaxed }

// Set up @Atomicity at the root
@Target(TargetKind.Program)
@Implicit
@type Atomicity(value: Atomicity = Atomicity.Nonatomic);

// Enum set computation here (TODO: check for Virgil syntax)
def AtomicTargets = [TargetKind.Container, TargetKind.Code, TargetKind.Field];

// This calculates implied Atomicity
@Target(AtomicTargets - TargetKind.Program)
@Implicit
@Derived  // means always computed automatically - user not allowed to specify
@type Atomicity(value: Atomicity = if(@This.Atomic, Atomicity.Atomic,
                                      if(@This.Relaxed, Atomicity.Relaxed, Atomicity.Nonatomic)));

// @Atomic: can be set explicitly with @Atomic, otherwise flows from atomicity
// of next outer construct, @Outer, a thing that allows queries of annotations.
// The @Auto means the value is set automatically, and *cannot* be set
// explicitly (this rules out @Atomic(false)); @Auto requires that a default
// be specified.
// @Implied's first argument is the implicit value of the field, and its
// second argument is the default value if @Atomic is givien explicitly.
// Note that we can omit .value if an annotation has a single field named .value.
@Target(AtomicTargets)
@Implicit
@type Atomic(@Auto value: bool = @Implied(@Outer.Atomicity == Atomicity.Atomic, true));

@Target(AtomicTargets)
@Implicit
@type Nonatomic(@Auto value: bool = @Implied(@Outer.Atomicity == Atomicity.Nonatomic, true));

@Target(AtomicTargets)
@Implicit
@type Relaxed(@Auto value: bool = @Implied(@Outer.Atomicity = Atomicity.Relaxed, true));

// Two derived annotations (not sure they need all these targets)
@Target(AtomicTargets)
@Implicit
@Derived
@type AtomicOk(value: bool = (@This.Atomic || @This.Relaxed));

@Target(AtomicTargets)
@Implicit
@Derived
@type NonatomicOk(value: bool = (@This.Nonatomic || @This.Relaxed));

None of the above does anything to a type *use* automatically.  We add this to
allow the possibility, but to make it manually controlled:

@Target(TargetKind.TypeUse)
@type Atomic(value: bool = true);

Summary of additional machinery:

- @Implicit: means that annotation is implicitly supplied on any included
  targets where an explicit annotation does not appear
- @This: means the current target; can be used to fetch annotation values
- @Outer.Ann: means the immediately containing target of a kind that supports
  Ann and to get the value of Ann for that target
- @Implied: indicated how to compute the implicit value, and default value for
  an explicit annotation of the kind being defined
- @Derived: indicates an annotation that is computed automatically from other
  annotations; the user cannot define it explicitly, but the its value can be
  used in computing annotation values, etc.

Examples:

class Vector<T> {
  var size: int;
  var elements: @Atomic(@Outer.Atomic) Array<T>;
  ...
}

With the above, at outer level and without any command line override, etc.,

def v1 = Vector<int>.new();
	// nonatomic all the way down

def v2 = @Atomic Vector<int>.new();
	// atomic, both for Vector and its contained Array.
	// We think of this as "cloning" the Vector class, giving a new
        // version with the @Atomic on the class.

def v3 = @Atomic Vector<Array<int>>.new();
	// The Vector and its contained Array are @Atomic, but the arrays *in* that
	// array are not.

def v4 = @Atomic Vector<@Atomic Array<int>>.new();
	// This makes the inner arrays atomic.

@atomic var v5 = Vector<int>.new();
	// The *variable* is atomic, but the objects it refers to are not.


A KEY POINT:  Annotating a type *use* creates an annotated *clone* of the type.


Implementation

Given that parameterized types may need to be instantiated, and annotated type
uses may cause further type cloning, it would seem that full expansion and
determination of annotation values will not be complete until reachability
analysis and normalization finish.

An annotation on a type use is a demand for a similarly annotated version of
the type being used.  The above is probably a little confused as to the
difference between writing an annotation directly on a type declaration
(class, variant, enum) and supplying it via annotating a type use.  Maybe we
need a way to say that thet TypeUse annotation clones the target type and
propagates the annotation to the target type.  Thus, Vector, above is agnostic
about atomicity, but has a notion of how to propagate atomicity to its
contained array.
